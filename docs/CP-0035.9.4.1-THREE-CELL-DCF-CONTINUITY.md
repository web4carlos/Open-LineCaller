# CP-0035.9.4.1 — Three-Cell DCF Continuity

## Purpose

Keep the active pickleball inside the existing Dynamic Court Field without
rediscovering it on every frame.

The DCF is unchanged:

- physical pickleball court: 20 ft × 44 ft;
- court resolution: 83 × 182 floor cells;
- Z resolution: 48 cells;
- external officiating margins remain part of `DynamicCourtField`;
- production DCF / mesh remains invisible.

## Core rule

```text
ONE ACTIVE BALL
      ↓
Cell(n-3) → Cell(n-2) → Cell(n-1)
                         ↓
              predict only nearby Cell(n)
                         ↓
                    accept SAME ball
```

The accepted history is hard-capped at three DCF cells.

## Search scope

Global Ball-in-Mesh remains acquisition / explicit reacquisition only.
During continuity, `track()` never performs a global search.

First handoff:

- immediate local DCF neighborhood only;
- max nominal neighborhood: 5 × 5 × 5 = 125 cells.

After two accepted cells:

- velocity comes from the short DCF history;
- predicted next location is searched in a nominal 3 × 3 × 3 neighborhood;
- one missed frame may add one local ring, never a full-field scan.

Because the active ball is already known, local continuity may use a lower
appearance threshold than global acquisition. The lower threshold applies
only inside this small DCF neighborhood.

## Contact rule

Two paths can trigger a floor-contact event:

```text
Z=... → Z=2 → Z=1, direction DOWN
                     ↓
             predict Cell(X,Y,0)
                     ↓
               FLOOR TRIGGER
```

or, when the camera skips Z=1 between frames:

```text
Z>1, direction DOWN → accepted Z=0
                           ↓
                     FLOOR TRIGGER
```

`floor_trigger=True` is evidence only. `floor_illumination` remains false in
this capability so the production glow renderer remains isolated in
CP-0035.9.5.

## Engineering visualization

`tools/dcf_three_cell_actual_mesh_gate.py` may render the ACTUAL DCF for
debugging:

- all 83 lateral floor divisions;
- all 182 depth floor divisions;
- the accepted current DCF cell;
- the last three accepted cells;
- the tiny next-cell candidate set;
- the predicted/accepted Z=0 contact cell.

This is an engineering view only. It does not introduce a second mesh and it
does not change production visibility.

## Clean-room note

This implementation was developed from LineCaller's existing DCF architecture.
No third-party Pickleball-Analytics source code, model weights, datasets, or
assets are incorporated by this capability pack.


## Ball-sized DCF cell invariant

CP-0035.9.4.1 formally locks the intended DCF scale:

```text
ONE PICKLEBALL ~= ONE DCF CELL
```

For the 20 ft x 44 ft pickleball court:

- X cell size = 240 in / 83 = about 2.892 in;
- Y cell size = 528 in / 182 = about 2.901 in;
- one Z step uses the same local projected scale as one lateral X cell.

Therefore Z is not an arbitrary visual height. With the default runtime vertical
vector, `Z=0` is the floor/contact plane and increasing Z moves upward. A falling
ball decreases Z toward zero.

This invariant is protected by automated tests so a future visualization or
camera profile cannot silently invert or rescale the physical DCF convention.
