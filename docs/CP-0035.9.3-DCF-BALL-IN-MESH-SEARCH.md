# CP-0035.9.3 RC2 — Runtime DCF Ball-in-Mesh Search

## Fixed architecture

LineCaller is pickleball-first.

The production algorithm must not contain constants for one particular court,
camera, or ball.

Runtime inputs:

- current court/camera calibration (`image_points`);
- current active ball reference;
- current Dynamic Court Field configuration.

## What RC2 fixes

### 1. Ball reference is background-independent

A user-provided ball crop can contain court/background pixels. RC2 isolates the
foreground ball automatically, recentres it internally, builds a mask, and
locks a color/appearance profile from ball pixels only.

No named color such as "yellow" is hardcoded.

### 2. No fixed camera Z constants

The old visual `PerspectiveCourtMesh` used `near_height_px` and `gamma`.
CP-0035.9.3 RC2 does not use those values for Ball-in-Mesh.

The runtime projector derives apparent DCF-cell scale from the current court
quadrilateral. Z is expressed in DCF-cell units and uses the current local
lateral DCF scale.

This is a runtime DCF projection model, not a camera-specific tuning.

### 3. Coarse-to-fine DCF search

Initial acquisition:

1. lock current ball identity;
2. create a per-frame similarity map from that ball;
3. coarse DCF hypothesis scan;
4. refine around the best DCF hypotheses;
5. masked appearance evaluation at strict projected cell centres;
6. return one `CellIndex(x,y,z)` or NOT FOUND.

The whole DCF is not intended to be rescanned every live frame.
CP-0035.9.4 will use the Ball Wave for local cell-to-cell tracking.

## Production visualization

DCF / mesh / Ball Wave stay invisible.

CP-0035.9.3 may mark the final found ball for evidence/debugging, but never
renders the mesh in production.

Floor illumination remains reserved for the Z=0 contact capability.
